# C++ Data Structures Implementation Plan

This document outlines the architecture and implementation strategy for the **C++ DSA Engine** (Module 3). The focus is on clean, "lab-style" implementations built from scratch, optimized for the Log Investigator use case.

## 1. Goals and Constraints
- **Lab-Style Implementation:** We will build the core data structures from scratch using pointers and standard arrays/vectors. We will strictly avoid "magic" inbuilt data structures like `std::map`, `std::set`, or `std::priority_queue`.
- **Clean Architecture:** Code will be heavily commented, clearly structured into headers (`.h`) and implementation files (`.cpp`), exactly as expected in a university setting or rigorous technical review.
- **CLI & JSON:** The entry point (`main.cpp`) will act as a CLI tool that takes arguments (passed from Node.js), runs the requested algorithms, measures execution time, and prints a strict JSON string to standard output.

## 3. Data Structure Designs

### A. The Shared Entity: `LogRecord`
- A struct holding: `id`, `timestamp`, `server`, `service`, `severity`, `message`, and calculated `priorityScore`.
- Memory Strategy: A master `std::vector<LogRecord>` will hold the actual data. The data structures (Tree, Trie, Heap) will store and pass around **pointers** (`LogRecord*`) to avoid duplicating memory.

### B. B+ Tree (Time-Range Indexing)
- **Why B+ Tree?** B+ Trees store all values in the leaf nodes, and the leaf nodes are linked together in a linked list. This makes range queries (e.g., "Find all logs between 14:30 and 14:35") incredibly fast: $O(\log N + K)$.
- **Implementation Details:**
  - `BPlusNode` struct containing: `bool isLeaf`, arrays of keys (timestamps), arrays of children pointers, and a `BPlusNode* next` pointer for leaf chaining.
  - Core functions to build from scratch: `insert()`, `splitChild()`, and `searchRange(start_time, end_time)`.

### C. Trie / Prefix Tree (Keyword Searching)
- **Why Trie?** Regular expressions are slow across millions of logs. A Trie allows us to find keywords in $O(L)$ time where $L$ is the length of the word, completely independent of how many logs exist.
- **Implementation Details:**
  - `TrieNode` struct containing an array of 256 pointers (representing ASCII characters) and a `std::vector<LogRecord*>` to store pointers to logs that contain the word ending at that node.
  - Core functions: `insert(word, log_ptr)` and `search(keyword)`.
  - When the engine starts, it will tokenize the `message` string of each log and insert each word into the Trie.

### D. Max-Heap (Priority Ranking)
- **Why Max-Heap?** We need to extract the top K most critical logs without sorting the entire dataset, which would be $O(N \log N)$. A heap allows finding the top K in $O(N + K \log N)$ time.
- **Implementation Details:**
  - Array-based binary tree representation (using `std::vector<LogRecord*>`).
  - Core functions to build from scratch: `insert()`, `extractMax()`, `heapifyUp()`, and `heapifyDown()`.
  - Priority logic: `score = severity_weight(CRITICAL=10, ERROR=7, etc) + recency_bonus`.

## 4. Execution Workflow (`main.cpp`)

1. **Parse Input:** Read the temporary `.log` file generated by Node.js.
2. **Parse Arguments:** 
   - `--bplus-start`, `--bplus-end`
   - `--trie-keys`
   - `--heap-topk`
3. **Pipeline Execution:** 
   - Only initialize and populate the data structures that the LLM requested.
   - Use `std::chrono` to measure the exact microsecond execution time of each operation.
4. **JSON Serialization:** Build a JSON string containing the final `evidence` array and the `dsa_metrics` array.
5. **Output:** `std::cout << jsonString;` (Node.js captures this).
